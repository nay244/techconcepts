# Fact-check: glossary group "transport"

Checked 2026-11-13 by a fresh fact-checker, from the claim sheet and the sources only. Every source was read in this run from the publisher's own site: the RFCs as plain text from the RFC Editor, the two ITU-T Recommendations and NIST SP 800-77r1 as PDFs (text kept with `pdftotext -raw`), and the Microsoft Learn page as HTML.

## The claims

### entry "ack", sense "tcp": statement "ack-tcp-1" — ✅

In TCP, ACK (acknowledge) is a flag in a segment's header: the segment's acknowledgment number gives the next byte the sender expects.

- `rfc-9293` §4
  > A control bit (acknowledge) occupying no sequence space, which indicates that the acknowledgment field of this segment specifies the next sequence number the sender of this segment is expecting to receive
- `rfc-9293` §3.1
  > If the ACK control bit is set, this field contains the value of the next sequence number the sender of the segment is expecting to receive.
  > … The control bits are also known as "flags".
- Note: RFC 9293 is the current TCP specification (Internet Standard, not obsoleted); its §3.1 defines the TCP header and its control bits, and its §4 glossary defines the ACK bit, so it is the defining standard for this flag and field.
- Note: "the next byte" says more loosely what the source calls the next sequence number; the SYN and FIN controls also take a sequence number, a detail the definition leaves out.
- Note: Currency: RFC 9293 is not obsoleted (RFC Editor info page, 2026-11-13).

### entry "ack", sense "tcp": statement "ack-tcp-2" — ✅

That confirms that every byte before it has arrived.

- `rfc-9293` §3.4
  > The acknowledgment mechanism employed is cumulative so that an acknowledgment of sequence number X indicates that all octets up to but not including X have been received.
- Note: RFC 9293 §3.4 defines TCP's sequence numbering and its cumulative acknowledgment, which is this claim.
- Note: Currency: RFC 9293 is current.

### entry "ack", sense "tcp": statement "ack-tcp-3" — ✅

Once a connection is open, every segment carries one.

- `rfc-9293` §3.1
  > Once a connection is established, this is always sent.
- `rfc-9293` §3.8
  > Note that, once in the ESTABLISHED state, all segments must carry current acknowledgment information.
- Note: RFC 9293 defines the TCP header (§3.1) and its data exchange (§3.8); both sections state the rule.
- Note: It leaves out rare exceptions, such as a reset sent when a program aborts a connection; the ordinary case is as stated.
- Note: Currency: RFC 9293 is current.

### entry "ack", sense "dhcp": statement "ack-dhcp-1" — ✅

In DHCP, the ACK (DHCPACK) is the message a DHCP server sends to confirm a client's request for an address.

- `rfc-2131` §3.1
  > DHCPACK - Server to client with configuration parameters, including committed network address.
  > … The server selected in the DHCPREQUEST message commits the binding for the client to persistent storage and responds with a DHCPACK message containing the configuration parameters for the requesting client.
- `microsoft-dhcp-basics` §DHCPACK
  > The DHCP server responds to the DHCPREQUEST with a DHCPACK, thus completing the initialization cycle.
- Note: RFC 2131 is the defining standard for DHCP (for IPv4) and defines its message types, DHCPACK among them; Microsoft's page states the same independently.
- Note: It leaves out the DHCPACK a server also sends for a lease renewal or in answer to a request for settings only; the ordinary case is as stated.
- Note: Currency: RFC 2131 is not obsoleted; its updates (such as RFC 4361 on client identifiers) do not change the DHCPACK's role. The Microsoft Learn page is live (updated 2025-09-22) and describes current Windows DHCP practice.

### entry "ack", sense "dhcp": statement "ack-dhcp-2" — ✅

It carries the address the client may now use, its other settings and how long the lease lasts.

- `rfc-2131` §3.1
  > The 'yiaddr' field in the DHCPACK messages is filled in with the selected network address.
  > … The client receives the DHCPACK message with configuration parameters. The client SHOULD perform a final check on the parameters (e.g., ARP for allocated network address), and notes the duration of the lease specified in the DHCPACK message.
- `microsoft-dhcp-basics` §DHCPACK
  > The YIADDR field contains the client's address
- Note: RFC 2131 defines the DHCPACK's contents: the address, the configuration parameters and the lease duration. The Microsoft page confirms the address field, and its captured DHCPACK shows the subnet mask, router and lease time.
- Note: Currency: both sources are current, as above.

### entry "connectionless": statement "connectionless-1" — ✅

Connectionless describes sending data without first setting up a connection: each message carries everything needed to deliver it and is handled on its own.

- `itu-x200` §5.3.3.3
  > Connectionless-mode transmission is the transmission of a single unit of data … without establishing a connection.
  > … all the information required to deliver a unit of data – destination address, quality of service selection, options, etc. – is presented to the layer providing the connectionless-mode service, together with the unit of data to be transmitted, in a single service access. The layer providing the connectionless-mode service is not required to relate this access to any other access.
- `rfc-8085` §1
  > UDP and its UDP-Lite variant [RFC3828] are unique in that they do not establish end-to-end connections between communicating end systems.
- Note: ITU-T X.200 (07/94), the OSI Basic Reference Model, defines connectionless-mode transmission (§5.3.3.3), so it is the defining standard for the term.
- Note: "carries everything needed to deliver it" puts in everyday words the source's rule that all the delivery information is handed over together with the unit of data.
- Note: Currency: ITU-T lists X.200 (07/94) as in force; RFC 8085 is a current Best Current Practice, not obsoleted.

### entry "connectionless": statement "connectionless-2" — ✅

UDP and IP work this way; TCP is connection-oriented.

- `rfc-1122` §1.1.3
  > TCP is a reliable connection-oriented transport service that provides end-to-end reliability, resequencing, and flow control. UDP is a connectionless ("datagram") transport service.
  > … IP is a connectionless or datagram internetwork service, providing no end-to-end delivery guarantees.
- `nist-sp800-77r1` §2.1
  > TCP, which provides reliable connection-oriented communications, and the User Datagram Protocol (UDP), which provides unreliable connectionless communications, are commonly used transport layer protocols.
- `rfc-791` §1.4
  > The internet protocol treats each internet datagram as an independent entity unrelated to any other internet datagram. There are no connections or logical circuits (virtual or otherwise).
- Note: Two independent sources (RFC 1122 and NIST SP 800-77r1) state the UDP and TCP parts; RFC 1122 and RFC 791 state the IP part.
- Note: Currency: RFC 1122 and RFC 791 are not obsoleted (their updates do not change these points; RFC 9293 §2.2 still calls TCP connection oriented). NIST SP 800-77r1 (June 2020) is final and not withdrawn or superseded.

### entry "connectionless": statement "connectionless-3" — ✅

With no connection to set up or tear down, there is little to keep track of.

- `rfc-8085` §1
  > UDP communication consequently does not incur connection establishment and teardown overheads, and there is minimal associated end-system state.
- `itu-x200` §5.3.3.3
  > In contrast to a connection, an instance of the use of a connectionless-mode service does not have a clearly distinguishable lifetime.
  > … it requires only a pre-arranged association between the peer-(N)-entities involved which determines the characteristics of the data to be transmitted, and no dynamic agreement is involved in an instance of the use of the service
- Note: X.200 defines connectionless mode, and states that no agreement is set up per use and that no access need be related to another, which is the small state this claim describes; RFC 8085 states it in so many words for UDP.
- Note: Currency: both sources are current, as above.

### entry "jitter": statement "jitter-1" — ✅

Jitter is variation in delay: packets of the same stream take different times to arrive.

- `itu-g114` §Annex A.3
  > Packetized transmission systems exhibit variable delay (jitter) in packet delivery time. This is caused by the fact that different packets carrying speech samples of the same telephone conversation may encounter varying queue lengths, or different routes through the network.
- `rfc-3550` §6.4.1
  > The interarrival jitter J is defined to be the mean deviation (smoothed absolute value) of the difference D in packet spacing at the receiver compared to the sender for a pair of packets.
- Note: Two independent sources: ITU-T G.114 and RFC 3550 (RTP), which defines the interarrival jitter it reports.
- Note: "the same stream" generalises the source's example of one telephone conversation.
- Note: Currency: ITU-T lists G.114 (05/2003) as in force, with its two amendments; RFC 3550 is not obsoleted, and its updates do not change the jitter field.

### entry "jitter": statement "jitter-2" — ✅

Voice calls hold packets briefly in a jitter buffer at the receiver, and a packet that arrives too late is thrown away.

- `itu-g114` §Annex A.3
  > This is typically achieved by collecting packets in a de-jitter buffer at the receive side.
  > … If the delivery time of a packet exceeds the length of the receive buffer, then this packet "arrives too late" with respect to its intended play-out time, and will be discarded.
- `rfc-3611` §4.7
  > The block reports separately on packets lost on the IP channel, and those that have been received but then discarded by the receiving jitter buffer.
- `rfc-3611` §4.7.1
  > The fraction of RTP data packets from the source that have been discarded since the beginning of reception, due to late or early arrival, under-run or overflow at the receiving jitter buffer.
- `rfc-3611` §4.7.7
  > This is the current maximum jitter buffer delay in milliseconds which corresponds to the earliest arriving packet that would not be discarded.
- Note: Two independent sources: ITU-T G.114 and RFC 3611, whose VoIP metrics count packets the receiving jitter buffer discards.
- Note: "briefly" is an everyday word for the buffer's delay (G.114's example is about 25 ms on average); "voice calls" means voice over IP, the case both sources describe.
- Note: Currency: G.114 is in force; RFC 3611 is not obsoleted (RFC Editor info page lists no obsoleting RFC).

### entry "retransmission": statement "retransmission-1" — ✅

Retransmission is sending data again because it seems to have been lost.

- `rfc-9293` §3.8
  > Because segments may be lost due to errors (checksum test failure) or network congestion, TCP uses retransmission to ensure delivery of every segment.
- `rfc-5681` §3.2
  > After receiving 3 duplicate ACKs, TCP performs a retransmission of what appears to be the missing segment, without waiting for the retransmission timer to expire.
- Note: RFC 9293 defines TCP's data exchange and its use of retransmission; RFC 5681 defines TCP's fast retransmit. They are two separate standards, and both state the meaning: sending again what appears lost.
- Note: Currency: RFC 9293 is current; RFC 5681 is not obsoleted (updated by RFC 9438, CUBIC, which does not change fast retransmit).

### entry "retransmission": statement "retransmission-2" — ✅

TCP resends a segment when no acknowledgment for it arrives before a timer runs out, or sooner when duplicate ACKs show it is missing.

- `rfc-6298` §5
  > When the retransmission timer expires, do the following:
  > (5.4) Retransmit the earliest segment that has not been acknowledged by the TCP receiver.
- `rfc-5681` §3.2
  > The fast retransmit algorithm uses the arrival of 3 duplicate ACKs (as defined in section 2, without any intervening ACKs which move SND.UNA) as an indication that a segment has been lost. After receiving 3 duplicate ACKs, TCP performs a retransmission of what appears to be the missing segment, without waiting for the retransmission timer to expire.
- `rfc-6298` §1
  > The Transmission Control Protocol (TCP) [Pos81] uses a retransmission timer to ensure data delivery in the absence of any feedback from the remote data receiver.
- Note: RFC 6298 defines TCP's retransmission timer and RFC 5681 defines fast retransmit on duplicate ACKs; each defines its half of the claim.
- Note: It leaves out the number (three duplicate ACKs) and newer loss-recovery methods.
- Note: Currency: RFC 6298 is not obsoleted; RFC 5681 is current, as above.

### entry "retransmission": statement "retransmission-3" — ✅

UDP does not retransmit: a program that needs lost data sent again must do it itself.

- `rfc-8085` §3.3
  > Application designers are generally aware that UDP does not provide any reliability, e.g., it does not retransmit any lost packets.
  > … Applications that do require reliable message delivery MUST implement an appropriate mechanism themselves.
- `rfc-1122` §4.1.1
  > Therefore, an application program running over UDP must deal directly with end-to-end communication problems that a connection-oriented protocol would have handled -- e.g., retransmission for reliable delivery, packetization and reassembly, flow control, congestion avoidance, etc., when these are required.
- Note: Two independent sources (RFC 8085 and RFC 1122). It leaves out that such a program may use a library or a protocol built over UDP for this; that is still the program's side, not UDP's.
- Note: Currency: RFC 8085 and RFC 1122 are not obsoleted.

### entry "sequence-number": statement "sequence-number-1" — ✅

In TCP, every byte of data sent over a connection has a sequence number, and each segment carries the number of its first byte.

- `rfc-9293` §3.4
  > A fundamental notion in the design is that every octet of data sent over a TCP connection has a sequence number.
- `rfc-9293` §3.1
  > The sequence number of the first data octet in this segment (except when the SYN flag is set).
- Note: RFC 9293 defines TCP's sequence numbers (§3.4) and the Sequence Number field (§3.1).
- Note: It leaves out the SYN exception, where the field holds the initial sequence number.
- Note: Currency: RFC 9293 is current.

### entry "sequence-number": statement "sequence-number-2" — ✅

The numbers let the receiver acknowledge what arrived, notice what is missing and put the bytes in order.

- `rfc-9293` §3.4
  > Since every octet is sequenced, each of them can be acknowledged.
- `rfc-9293` §2.2
  > TCP reliability consists of detecting packet losses (via sequence numbers) and errors (via per-segment checksums), as well as correction via retransmission.
- `rfc-9293` §3.10.7.4
  > In the following it is assumed that the segment is the idealized segment that begins at RCV.NXT and does not exceed the window.
  > … Segments with higher beginning sequence numbers SHOULD be held for later processing (SHLD-31).
- `rfc-1122` §1.1.3
  > TCP is a reliable connection-oriented transport service that provides end-to-end reliability, resequencing, and flow control.
- Note: RFC 9293 defines TCP's sequence numbers and their processing on arrival; a segment that starts past the next expected number shows a gap, and it is held until the missing bytes come, which is putting them in order. RFC 1122 names the resequencing.
- Note: Currency: RFC 9293 and RFC 1122 are current.

### entry "sequence-number": statement "sequence-number-3" — ✅

Each side chooses its own starting number when the connection opens.

- `rfc-9293` §3.4.1
  > For each connection there is a send sequence number and a receive sequence number. The initial send sequence number (ISS) is chosen by the data sending TCP peer, and the initial receive sequence number (IRS) is learned during the connection-establishing procedure.
  > … The synchronization requires each side to send its own initial sequence number
- Note: RFC 9293 §3.4.1 defines initial sequence number selection.
- Note: Currency: RFC 9293 is current.

### entry "tcp": statement "tcp-1" — ✅

TCP (Transmission Control Protocol) is a transport protocol that gives programs a reliable, in-order stream of bytes, sent over IP.

- `rfc-9293` §2.2
  > TCP provides a reliable, in-order, byte-stream service to applications.
  > The application byte-stream is conveyed over the network via TCP segments, with each TCP segment sent as an Internet Protocol (IP) datagram.
- `rfc-9293` §1
  > In 1981, RFC 793 [16] was released, documenting the Transmission Control Protocol (TCP) and replacing earlier published specifications for TCP.
  > Since then, TCP has been widely implemented, and it has been used as a transport protocol for numerous applications on the Internet.
- `rfc-1122` §1.1.3
  > There are two primary transport layer protocols at present:
- Note: RFC 9293 is the defining standard for TCP; it gives the full name and the service. RFC 1122 places TCP in the transport layer (it lists TCP right after the quoted line).
- Note: Currency: RFC 9293 and RFC 1122 are current.

### entry "tcp": statement "tcp-2" — ✅

It opens a connection before data flows, numbers every byte and sends again whatever is lost.

- `rfc-9293` §2.2
  > TCP reliability consists of detecting packet losses (via sequence numbers) and errors (via per-segment checksums), as well as correction via retransmission.
  > … TCP is connection oriented, though it does not inherently include a liveness detection capability.
- `rfc-9293` §3.4
  > A fundamental notion in the design is that every octet of data sent over a TCP connection has a sequence number.
- `rfc-9293` §3.8
  > Once the connection is established, data is communicated by the exchange of segments. Because segments may be lost due to errors (checksum test failure) or network congestion, TCP uses retransmission to ensure delivery of every segment.
- Note: RFC 9293 defines all three behaviours.
- Note: It leaves out that a SYN may carry data that is held until the connection is open (§3.5), and that a connection that fails outright stops resending.
- Note: Currency: RFC 9293 is current.

### entry "tcp": statement "tcp-3" — ✅

Port numbers tell apart the programs using it.

- `rfc-9293` §2.2
  > TCP uses port numbers to identify application services and to multiplex distinct flows between hosts.
- Note: RFC 9293 defines TCP's use of ports. "Programs" says loosely what the source calls application services and flows.
- Note: Currency: RFC 9293 is current.

### entry "tcp-connection": statement "tcp-connection-1" — ✅

A TCP connection is a path for data that two programs set up through TCP before they exchange data.

- `rfc-9293` §4
  > A logical communication path identified by a pair of sockets.
- `rfc-9293` §3.8
  > Once the connection is established, data is communicated by the exchange of segments.
- Note: RFC 9293's glossary defines a TCP connection; §3.8 says data flows once it is established.
- Note: "Two programs set up" is loose: the programs ask for it and their TCP endpoints set it up, which is what "through TCP" says.
- Note: Currency: RFC 9293 is current.

### entry "tcp-connection": statement "tcp-connection-2" — ✅

It is identified by the IP address and port at each end.

- `rfc-9293` §4
  > A logical communication path identified by a pair of sockets.
  > … An address that specifically includes a port identifier, that is, the concatenation of an Internet Address with a TCP port.
- Note: RFC 9293's glossary defines both the connection and the socket (address and port), which together give the claim.
- Note: Currency: RFC 9293 is current.

### entry "tcp-connection": statement "tcp-connection-3" — ✅

It is opened by the three-way handshake, carries data both ways, and is closed when they are done.

- `rfc-9293` §3.5
  > The "three-way handshake" is the procedure used to establish a connection.
- `rfc-9293` §2.2
  > Data flow is supported bidirectionally over TCP connections, though applications are free to send data only unidirectionally, if they so choose.
- `rfc-9293` §3.6
  > CLOSE is an operation meaning "I have no more data to send."
- Note: RFC 9293 defines opening (§3.5) and closing (§3.6) a connection.
- Note: It leaves out a connection that is reset or aborted, and programs that send only one way; the ordinary case is as stated.
- Note: Currency: RFC 9293 is current.

### entry "three-way-handshake": statement "three-way-handshake-1" — ✅

The three-way handshake is how TCP opens a connection: a SYN, a SYN and ACK in reply, then an ACK.

- `rfc-9293` §3.5
  > The "three-way handshake" is the procedure used to establish a connection.
  > … In line 3, TCP Peer B sends a SYN and acknowledges the SYN it received from TCP Peer A.
  > … At line 4, TCP Peer A responds with an empty segment containing an ACK for TCP Peer B's SYN
- Note: RFC 9293 §3.5 defines the procedure; line 2 of its Figure 6 is the first SYN.
- Note: It leaves out the rarer simultaneous open, which the same section also allows.
- Note: Currency: RFC 9293 is current.

### entry "three-way-handshake": statement "three-way-handshake-2" — ✅

Through it, each side tells the other the sequence number it will start from and confirms the other's.

- `rfc-9293` §3.4.1
  > The synchronization requires each side to send its own initial sequence number and to receive a confirmation of it in acknowledgment from the remote TCP peer. Each side must also receive the remote peer's initial sequence number and send a confirming acknowledgment.
  > … Because steps 2 and 3 can be combined in a single message this is called the three-way (or three message) handshake (3WHS).
- Note: RFC 9293 §3.4.1 defines this exchange of initial sequence numbers.
- Note: Currency: RFC 9293 is current.

### entry "three-way-handshake": statement "three-way-handshake-3" — ✅

It also stops an old, delayed request from opening a connection by mistake.

- `rfc-9293` §3.5
  > The principal reason for the three-way handshake is to prevent old duplicate connection initiations from causing confusion.
- Note: RFC 9293 §3.5 defines the handshake and states its reason; its Figure 8 shows an old duplicate SYN turned away by a reset.
- Note: Currency: RFC 9293 is current.

### entry "udp": statement "udp-1" — ✅

UDP (User Datagram Protocol) is a transport protocol that lets a program send a message, a datagram, to another program over IP with a minimum of machinery.

- `rfc-768` §Introduction
  > This User Datagram Protocol (UDP) is defined to make available a datagram mode of packet-switched computer communication in the environment of an interconnected set of computer networks. This protocol assumes that the Internet Protocol (IP) [1] is used as the underlying protocol.
  > This protocol provides a procedure for application programs to send messages to other programs with a minimum of protocol mechanism.
- `rfc-8085` §1
  > The User Datagram Protocol (UDP) [RFC768] provides a minimal, unreliable, best-effort, message-passing transport to applications and other protocols (such as tunnels) that wish to operate over IP.
- Note: RFC 768 is the defining standard for UDP and gives its full name; RFC 8085 confirms it is a transport.
- Note: Currency: RFC 768 is not obsoleted; it is updated by RFC 9868 (UDP options), whose abstract and text keep UDP a stateless, unreliable protocol, so the claim holds. RFC 8085 is current.

### entry "udp": statement "udp-2" — ✅

It sets up no connection, and delivery, order and protection from duplicates are not guaranteed.

- `rfc-768` §Introduction
  > The protocol is transaction oriented, and delivery and duplicate protection are not guaranteed.
- `rfc-8085` §1
  > UDP and its UDP-Lite variant [RFC3828] are unique in that they do not establish end-to-end connections between communicating end systems.
- `rfc-8085` §3.3
  > UDP also does not protect against datagram duplication, i.e., an application may receive multiple copies of the same UDP datagram, with some duplicates arriving potentially much later than the first.
  > … Applications that require ordered delivery MUST reestablish datagram ordering themselves.
- `rfc-1122` §1.1.3
  > UDP is a connectionless ("datagram") transport service.
- Note: RFC 768 defines UDP and states delivery and duplicates; RFC 8085 and RFC 1122 confirm the connection and order parts.
- Note: Currency: all current, as above.

### entry "udp": statement "udp-3" — ✅

Programs that need those use TCP, or provide them themselves.

- `rfc-768` §Introduction
  > Applications requiring ordered reliable delivery of streams of data should use the Transmission Control Protocol (TCP) [2].
- `rfc-8085` §3.3
  > Applications that do require reliable message delivery MUST implement an appropriate mechanism themselves.
- `rfc-1122` §4.1.1
  > Therefore, an application program running over UDP must deal directly with end-to-end communication problems that a connection-oriented protocol would have handled
- Note: RFC 768 defines UDP and points to TCP; RFC 8085 and RFC 1122 state the do-it-yourself path.
- Note: It leaves out other standard transports that RFC 8085 also recommends; the sentence does not say "only", so it rules nothing out.
- Note: Currency: all current, as above.
