## Entry: datagram

### entry "datagram": names — ✅

- Note: The only name is "Datagram". Statements datagram-1 to datagram-3 all use it for this thing, and RFC 791 §1.1 and RFC 1122 §1.3.3 give it as the name of IP's unit of data.

### entry "datagram": statement "datagram-1" — ✅

Text: "A datagram is a message that travels on its own: the network handles each one separately, with no connection set up first."

- `rfc-791` §1.4
  > The internet protocol treats each internet datagram as an independent
  > entity unrelated to any other internet datagram. There are no
  > connections or logical circuits (virtual or otherwise).
- Note: RFC 791 is the defining standard for IP and its datagram, the original datagram service. It is not obsoleted, and its updates (RFC 1349, 2474, 6864) touch the ToS/DS and ID fields only.
- `rfc-1812` §2.2.1
  > IP is a connectionless or datagram internetwork service
- `rfc-9293` §4
  > A message sent in a packet-switched computer communications network.
- Note: RFC 791 and RFC 1812 are two separate standards, and each states that datagrams are handled independently with no connection. RFC 9293's glossary supports "a message".
- Note: Currency: none of the three RFCs is obsoleted (RFC Editor info pages, 2026-11-13).

### entry "datagram": statement "datagram-2" — ✅

Text: "IP’s unit of data is the IP datagram, and UDP’s messages are user datagrams."

- `rfc-1122` §1.3.3
  > An IP datagram is the unit of end-to-end transmission in
  > the IP protocol.
- `rfc-791` §1.1
  > The internet protocol provides for
  > transmitting blocks of data called datagrams from sources to
  > destinations
- Note: RFC 791 defines IP and names its unit of data the datagram.
- `rfc-768` §Fields
  > Length is the length in octets of this user datagram including this header and the data.
- Note: RFC 768 defines UDP and calls each UDP message a user datagram. RFC 768 is updated by RFC 9868 (UDP options), which does not change this name.

### entry "datagram": statement "datagram-3" — ✅

Text: "Delivery is not guaranteed: a datagram may arrive damaged, duplicated, out of order or not at all."

- `rfc-1812` §2.2.1
  > IP datagrams may arrive at the
  > destination host damaged, duplicated, out of order, or not at all.
- `rfc-768` §Introduction
  > delivery and duplicate protection are not guaranteed.
- Note: RFC 768 defines UDP's datagram service and states that delivery is not guaranteed. RFC 1812 gives the four outcomes word for word.
- Note: Currency: RFC 1812 is updated by RFC 2644 and RFC 6633, neither of which touches this.

### entry "datagram": lessons — ✅

- Note: The `what-is-udp` term "Datagram" (one message that travels on its own) names the same thing in the same sense as datagram-1, more plainly. It contradicts nothing in the definition.

## Entry: forwarding

### entry "forwarding": names — ✅

- Note: "Forwarding" is used for this thing by forwarding-1. RFC 1812 §2.2.3 also names the choice "relaying or forwarding".

### entry "forwarding": statement "forwarding-1" — ✅

Text: "Forwarding is what a router does with a packet that is not addressed to it: it sends the packet on toward its destination."

- `rfc-1812` §5.2.1.1
  > The IP datagram is not destined for the router, and should be
  > queued for forwarding.
- Note: RFC 1812 is the current standard that defines the IPv4 router's forwarding algorithm (§5.2.1).
- `rfc-8200` §2
  > router a node that forwards IPv6 packets not explicitly
  > addressed to itself.
- Note: RFC 8200 is the IPv6 standard, and §2 defines a router as a node that forwards packets not addressed to itself. It is not obsoleted, and its one update (RFC 9673, Hop-by-Hop options) does not affect this.
- Note: "toward its destination" puts the meaning of forwarding into everyday words. Neither section states it in those words, but RFC 1812 §5.2.1.2 (cited by forwarding-2) does it through the next hop, so a beginner is not misled.

### entry "forwarding": statement "forwarding-2" — ✅

Text: "It looks up the destination in its routing table to choose the next hop: the next router or, on the last hop, the destination host."

- `rfc-1812` §2.2.3
  > Forwarding
  > an IP datagram generally requires the router to choose the address
  > and relevant interface of the next-hop router or (for the final hop)
  > the destination host. This choice, called relaying or forwarding
  > depends upon a route database within the router. The route database
  > is also called a routing table or forwarding table.
- `rfc-1812` §5.2.1.2
  > The forwarder determines the next hop IP address for the packet,
  > usually by looking up the packet's destination in the router's
  > routing table.
- Note: RFC 1812 defines the IPv4 forwarding algorithm, including the next-hop lookup. The statement leaves out the source's "usually" (other lookups exist), which is a simplification true in the ordinary case.

### entry "forwarding": lessons — ✅

- Note: The `what-is-ip` term "Forwarding" (passing a packet on to the next router) names the same thing. It leaves out the last hop to the destination host, so it is thinner than the definition but does not contradict it.

## Entry: frame

### entry "frame": names — ✅

- Note: "Frame" is used for this thing by frame-1 and frame-2, and RFC 1122 §1.3.3 gives it as a term.

### entry "frame": statement "frame-1" — ✅

Text: "A frame is the unit of data that a link layer protocol, such as Ethernet, sends: a link-layer header followed by a packet."

- `rfc-1122` §1.3.3
  > A frame is the unit of transmission in a link layer
  > protocol, and consists of a link-layer header followed by
  > a packet.
- `microsoft-osi` §Data link layer
  > The data link layer sends frames between physical addresses
- `rfc-894` §Frame Format
  > IP datagrams are transmitted in standard Ethernet frames. The type
  > field of the Ethernet frame must contain the value hexadecimal 0800.
  > The data field contains the IP header followed immediately by the IP
  > data.
- Note: Three independent documents (two RFCs and Microsoft's page) say the frame is the link layer's unit. RFC 894 gives Ethernet as the example, and its frame carries the IP packet after its own fields.
- Note: The statement leaves out the trailer an Ethernet frame ends with (the frame check sequence). This is a simplification: RFC 1122 itself defines a frame as a header followed by a packet.

### entry "frame": statement "frame-2" — ✅

Text: "A router takes the packet out of the frame it arrived in and sends it on in a new frame for the next link."

- `rfc-1812` §1
  > It generally removes the Link Layer header a
  > message was received with, modifies the IP header, and replaces the
  > Link Layer header for retransmission.
- `rfc-1812` §5.2.1.2
  > The forwarder encapsulates the IP datagram (or each of the
  > fragments thereof) in an appropriate Link Layer frame and queues
  > it for output on the interface selected in step 5.
- Note: RFC 1812 is the current standard defining what an IPv4 router does with a packet it forwards.
- `rfc-791` §2.2
  > The datagram arrives at a gateway host wrapped in the local network
  > header, the local network interface strips off this header, and
  > turns the datagram over to the internet module.
- Note: RFC 791 defines IP's model of operation. It goes on to say that the gateway's interface on the next network creates a new local network header.

## Entry: header

### entry "header": names — ✅

- Note: "Header" is used for this thing by header-layer-1 and header-http-1. "Header field" is given by header-http-1 as HTTP's full name for headers, and RFC 9110 §6.3 says the same.

### entry "header", sense "layer": label — ✅

- Note: "In the layer model" names where this sense applies. Both statements are about headers that protocol layers add.

### entry "header", sense "layer": statement "header-layer-1" — ✅

Text: "A header is control information, such as addresses, that a protocol puts at the front of the data it carries."

- `rfc-9293` §4
  > Control information at the beginning of a message, segment,
  > fragment, packet, or block of data.
- `nist-sp800-77r1` §2.1, footnote 6
  > At each layer, the logical units are typically composed of a header and a payload. The payload consists of the information
  > passed down from the previous layer, while the header contains layer-specific information such as addresses.
- Note: An RFC and a NIST publication are two independent sources. RFC 9293 says a header is control information at the front, and NIST says what it holds (addresses, for example) and that it goes with the data passed down to the layer.
