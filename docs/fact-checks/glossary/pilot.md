## Destination unreachable

### entry "destination-unreachable": names — ✅

- Note: The only name is the term itself, "Destination unreachable". Both of the entry's statements use it as the name of this ICMP message, and RFC 792 and RFC 1812 name the message the same way in the sections cited. No other spelling is shown.

### entry "destination-unreachable": statement "destination-unreachable-1" — ✅

Claim: Destination unreachable is the ICMP message sent back to a packet's sender when the packet cannot be delivered.

- `rfc-1812` §5.2.7.1
  > The ICMP Destination Unreachable message is sent by a router in
  > response to a packet which it cannot forward because the destination
  > (or next hop) is unreachable or a service is unavailable.
- Note: RFC 1812 is the current Standards Track requirements document for IPv4 routers, and this section defines when a router generates this message. The marker is correct.
- `rfc-792` §Destination Unreachable Message, page 5
  > If, in the destination host, the IP module cannot deliver the
  > datagram  because the indicated protocol module or process port is
  > not active, the destination host may send a destination
  > unreachable message to the source host.
- Note: RFC 792 defines ICMP and this message type (type 3). The marker is correct.
- Note: True for a beginner. The statement leaves out that sending the message is permitted rather than always done ("may" in RFC 792), and that a packet discarded because its TTL ran out gets a time exceeded message instead (that case is the group's own time exceeded entry). Neither omission would leave a beginner believing something false about what this message is.
- Note: Currency. RFC 792 is not obsoleted; its updates (RFC 950, 4884, 6633, 6918) leave this message's meaning as it was. RFC 1812 is not obsoleted; its updates (RFC 2644, 6633) do not touch §5.2.7.1.

### entry "destination-unreachable": statement "destination-unreachable-2" — ✅

Claim: A router sends it when it has no route to the destination; the destination itself sends it when nothing there is using the protocol or port the packet was for.

- `rfc-792` §Destination Unreachable Message, page 4
  > 0 = net unreachable;
  > 1 = host unreachable;
  > 2 = protocol unreachable;
  > 3 = port unreachable;
- `rfc-792` §Destination Unreachable Message, page 5
  > If, according to the information in the gateway's routing tables,
  > the network specified in the internet destination field of a

  > to the internet source host of the datagram.
- `rfc-792` §Destination Unreachable Message, page 5
  > If, in the destination host, the IP module cannot deliver the
  > datagram  because the indicated protocol module or process port is
  > not active, the destination host may send a destination
  > unreachable message to the source host.
- `rfc-1812` §5.2.7.1
  > messages
  > addressed to network prefixes for which the router has no valid
  > route.
- Note: RFC 792 defines the message and its codes, and RFC 1812 defines when a router generates it. Both markers are correct; they are two independent standards that agree.

## Echo reply

### entry "echo-reply": names — ✅

- Note: The only name is the term, "Echo reply". Both statements use it for this message; RFC 792 and RFC 1122 name it "echo reply" / "Echo Reply" in the sections cited.

### entry "echo-reply": statement "echo-reply-1" — ✅

Claim: An echo reply is the ICMP message a device sends back when it receives an echo request.

- `rfc-792` §Echo or Echo Reply Message, page 14
  > The address of the source in an echo message will be the
  > destination of the echo reply message.  To form an echo reply
  > message, the source and destination addresses are simply reversed,
  > the type code changed to 0, and the checksum recomputed.
- Note: RFC 792 defines the echo and echo reply messages (types 8 and 0). The marker is correct.
- `rfc-1122` §3.2.2.6
  > Every host MUST implement an ICMP Echo server function that
  > receives Echo Requests and sends corresponding Echo Replies.
- Note: True for a beginner. It leaves out that an echo request sent to a broadcast or multicast address may be silently discarded (RFC 1122 §3.2.2.6), and that some devices are configured not to answer.
- Note: Currency. RFC 792 and RFC 1122 are not obsoleted; their updates do not change the echo function.

### entry "echo-reply": statement "echo-reply-2" — ✅

Claim: It carries the request's data back to the sender, which learns that the device was reached and how long the answer took.

- `rfc-792` §Echo or Echo Reply Message, page 15
  > The data received in the echo message must be returned in the echo
  > reply message.
- Note: RFC 792 defines the echo reply and requires the data to be returned in it. The marker is correct.
- `microsoft-ping` §Introduction
  > Verifies IP-level connectivity to another TCP/IP computer by sending Internet Control Message Protocol (ICMP) echo Request messages. The receipt of the corresponding echo Reply messages is displayed, along with round-trip times.
- `rfc-2151` §3.2
  > Ping uses a series of Internet Control Message Protocol
  > (ICMP) [22] Echo messages to determine if a remote host is active or
  > inactive, and to determine the round-trip delay in communicating with
  > it.
- `cisco-ping-traceroute` §Performance
  > You can obtain the round-trip time (RTT) with the ping and traceroute commands. This is the time required to send an echo packet and get an answer back.
- Note: "Back to the sender" rests on RFC 792 (the reply goes to the echo's source address); "reached" and "how long" rest on Microsoft, RFC 2151 and Cisco, which are independent of each other. True for a beginner: the sender learns the time by timing the exchange, which is what these sources describe.
- Note: Currency. The Microsoft page is live (dated 2023-09-15) and describes the current Windows ping; the Cisco page is live (recertified 3 September 2026); RFC 2151 is Informational and not obsoleted.

### entry "echo-reply": lessons — ✅

- Note: `what-is-icmp` `term-echo-reply` ("Echo reply", idea "Yes, I'm here") names the same message. The idea is a plain gloss of answering an echo request and does not contradict the definition.

  > A name indicates what we seek.  An address indicates where it is.

  > Addresses are fixed length of four octets (32 bits).

- `rfc-791` §1.4
  > The internet modules use the addresses carried in the internet header

- Note: True for a beginner. Both sources describe the 32-bit IPv4 address; the statement says "number" without a size, which also holds for IPv6. That an address belongs to a connection rather than the whole device is the next statement's point.
- Note: Currency. RFC 791 is not obsoleted; its updates (RFC 1349, 2474, 6864) do not change addressing. The Microsoft page is live (dated 2026-02-12).

### entry "ip-address": statement "ip-address-2" — ✅

Claim: It is given to a network connection, so a device with several connections has several addresses.

- `rfc-8200` §2
  > interface    a node's attachment to a link.
- `rfc-8200` §2
  > address      an IPv6-layer identifier for an interface or a set of

- Note: RFC 8200 is the Internet Standard that defines IPv6, and its §2 defines the terms "interface" and "address". The marker is correct.
- `rfc-791` §2.3
  > Some hosts will also have several physical
  > interfaces (multi-homing).

  > That is, provision must be made for a host to have several physical

  > addresses.
- Note: RFC 791 defines IPv4 addressing; the marker is correct, and it is a different standard from RFC 8200.
- Note: True for a beginner. "Network connection" is an everyday word for an interface. It leaves out that one interface may have several addresses, and addresses that name a set of interfaces.
- Note: Currency. RFC 8200 is not obsoleted; its one update (RFC 9673, Hop-by-Hop options) does not touch §2. RFC 791 as above.

### entry "ip-address": statement "ip-address-3" — ✅

Claim: It is unique within its own network; private addresses are reused on other networks.

- `microsoft-tcpip-subnetting` §IP addresses: Networks and hosts
  > An IP address is a 32-bit number. It uniquely identifies a host (computer or other device, such as a printer or router) on a TCP/IP network.
- `rfc-1918` §3
  > The address space can thus be used
  > by many enterprises. Addresses within this private address space will
  > only be unique within the enterprise, or the set of enterprises which
  > choose to cooperate over this space
- Note: RFC 1918 (BCP 5) defines the private address space and how it may be used. The marker is correct.
- Note: "Unique" is stated by both sources: Microsoft for an address on its network, RFC 1918 for private addresses within the enterprise. Public addresses are globally unique (RFC 1918 §3), which is consistent with "unique within its own network".
- Note: Currency. RFC 1918 is not obsoleted; its one update (RFC 6761) concerns special-use domain names, not this section. The Microsoft page is live.

### entry "ip-address": lessons — ✅

- Note: Four tied terms, each "IP address": `dhcp` and `what-is-dhcp` `term-ip` ("The laptop's own number on the network, so messages can find it"), `what-is-http` `term-ip` ("Where to send it: the server's number") and `what-is-ip` `term-ip` ("The number that says where a device is"). ## Packet loss

### entry "packet-loss": names — ✅

- Note: The only name is the term, "Packet loss". Both statements use it; RFC 7680 names the metric "One-way Packet Loss" and the Azure and Cisco pages say "packet loss".

### entry "packet-loss": statement "packet-loss-1" — ✅

Claim: Packet loss is packets that are sent but do not arrive.

- `rfc-7680` §2.4
  > >>The *Type-P-One-way-Packet-Loss* from Src to Dst at T is 1<< means
  > that Src sent the first bit of a Type-P packet to Dst at wire time T
  > and that Dst did not receive that packet
- `rfc-792` §Introduction
  > Some datagrams may still be
  > undelivered without any report of their loss.
- Note: Two independent RFCs. RFC 7680 defines loss as sent but not received; RFC 792 calls undelivered datagrams lost.
- Note: True for a beginner. It leaves out RFC 7680's waiting threshold and its rule that a corrupted packet counts as lost.
- Note: Currency. RFC 7680 (Standards Track, obsoletes RFC 2680) is not obsoleted. RFC 792 as above.

### entry "packet-loss": statement "packet-loss-2" — ✅

Claim: Ping shows it as the share of its echo requests that got no reply, such as 1 lost out of 6.

- `rfc-2151` §3.2
  > 6 packets transmitted, 5 packets received, 16% packet loss
- `rfc-2151` §3.2
  > -c Count    Specifies the number of Echo Requests to be sent
- `microsoft-ping` §Parameters
  > If the echo Reply message isn't received within the time-out, the "Request timed out" error message is displayed.
- `microsoft-azure-tcpip-tuning` §Measure round-trip time and packet loss
  > The output of PING shows the minimum/maximum/average latency between a source and destination. It shows packet loss.
- `cisco-ping-traceroute` §Ping Command
  > Success rate is 0 percent (0/5)
- Note: RFC 2151's example is the one the statement gives (six sent, five received, shown as a percentage lost). The Cisco page shows the same count as a share of replies received, and the Azure page says ping's output shows packet loss: these are independent of RFC 2151 and of each other. The Microsoft parameters section supports only the "got no reply" part (each unanswered request is reported); it does not show the share.
- Note: Currency. All four pages are live and describe current ping tools.

### entry "packet-loss": lessons — ✅

- Note: `what-is-icmp` `term-loss` ("Packet loss", idea "Pings that never come back") names the same thing, narrowed to ping. A thinner line than the definition, it does not contradict it.

## Time exceeded

### entry "time-exceeded": names — ✅

- Note: The only name is the term, "Time exceeded". All three statements use it, and RFC 792 and RFC 1812 name the message "Time Exceeded".

### entry "time-exceeded": statement "time-exceeded-1" — ✅

Claim: Time exceeded is the ICMP message a router sends back to a packet's sender when it throws the packet away because its TTL ran out.

- `rfc-792` §Time Exceeded Message, page 6
  > If the gateway processing a datagram finds the time to live field
  > … is zero it must discard the datagram.  The gateway may also notify
  > the source host via the time exceeded message.
- Note: RFC 792 defines this message (type 11, code 0 "time to live exceeded in transit"). The passage runs across the break between pages 6 and 7. The marker is correct.
- `rfc-1812` §5.2.7.3
  > A router MUST generate a Time Exceeded message Code 0 (In Transit)
  > when it discards a packet due to an expired TTL field.
- Note: RFC 1812 defines the router's duty to send it. The marker is correct.
- Note: True for a beginner. It leaves out that a router may have the message switched off on an interface (RFC 1812 §5.2.7.3), and the reassembly case, which is this entry's third statement.
- Note: Currency as for RFC 792 and RFC 1812 above.

### entry "time-exceeded": statement "time-exceeded-2" — ✅

Claim: Traceroute depends on these messages.

- `rfc-1812` §5.3.1
  > ICMP Time Exceeded messages are required because the traceroute
  > diagnostic tool depends on them.
- `microsoft-tracert` §Introduction
  > The path is determined by examining the ICMP time Exceeded messages returned by intermediate routers and the echo Reply message returned by the destination.
- Note: Two independent sources, a standard and a vendor page. Currency: RFC 1812 is not obsoleted; the Microsoft page is live (dated 2023-09-27) and describes the current tracert.

### entry "time-exceeded": statement "time-exceeded-3" — ✅

Claim: A host may also send one when it gives up putting a split packet back together.

- `rfc-792` §Time Exceeded Message, page 7
  > If a host reassembling a fragmented datagram cannot complete the
  > reassembly due to missing fragments within its time limit it
  > discards the datagram, and it may send a time exceeded message.
- Note: RFC 792 defines the time exceeded message and its code 1, fragment reassembly time exceeded. The marker is correct, and RFC 792 is the current definition of this ICMPv4 message.
- Note: "Split packet" is an everyday word for a fragmented datagram, and "gives up" for not completing reassembly within the time limit.

### entry "time-exceeded": lessons — ✅

- Note: `what-is-icmp` `term-time-exceeded` ("Time exceeded", idea "Your packet ran out of hops here") names the same message in the TTL sense of the first statement. The idea does not contradict the definition.

## Traceroute

### entry "traceroute": names — ✅

- Note: The only name is the term, "Traceroute". Both statements use it, and RFC 2151 and Cisco name the tool traceroute (Microsoft's command is tracert, and the page calls it the same tool by its function).

### entry "traceroute": statement "traceroute-1" — ✅

Claim: Traceroute is a tool that shows the route packets take to a device, one router at a time.

- `rfc-2151` §3.4
  > Traceroute is another common TCP/IP tool, this one allowing users to
  > learn about the route that packets take from their local host to a
  > remote host.
- `microsoft-tracert` §Introduction
  > This diagnostic tool determines the path taken to a destination by sending Internet Control Message Protocol (ICMP) echo Request or ICMPv6 messages to the destination with incrementally increasing time to live (TTL) field values.
- `cisco-ping-traceroute` §Traceroute Command
  > The traceroute command is used to discover the routes that packets actually take when they travel to their destination.
- Note: "One router at a time" is the TTL-step method that RFC 2151, Microsoft and Cisco each describe; the Microsoft page says the path shown is the list of routers in the path.
- Note: Currency. The pages are live; RFC 2151 is not obsoleted.

### entry "traceroute": statement "traceroute-2" — ✅

Claim: It sends probes with a TTL of 1, then 2, then 3, and the router where each probe's TTL runs out normally sends back a time exceeded message, so the routers appear in order.

- `microsoft-tracert` §Introduction
  > This command determines the path by sending the first echo Request message with a TTL of 1 and incrementing the TTL by 1 on each subsequent transmission until the target responds or the maximum number of hops is reached.
- `microsoft-tracert` §Introduction
  > However, some routers don't return time Exceeded messages for packets with expired TTL values and are invisible to the tracert command.
- `rfc-2151` §3.4
  > The TTL value of 1 causes the datagram to "timeout" as soon as
  > it hits the first router in the path; this router will then respond
  > with an ICMP Time Exceeded Message (TEM) indicating that the datagram
  > has expired. Another three UDP messages are now sent, each with the
  > TTL value set to 2, which causes the second router to return ICMP
- `rfc-1812` §5.3.1
  > If the TTL is reduced to zero (or less), the packet MUST be
  > discarded, and if the destination is not a multicast address the
  > router MUST send an ICMP Time Exceeded message, Code 0 (TTL Exceeded
  > in Transit) message to the source.
- `cisco-ping-traceroute` §Traceroute Command
  > Three datagrams are sent, each with a Time-To-Live (TTL) field value set to one. The TTL value of 1 causes the datagram to "timeout" as soon as it hits the first router in the path; this router then responds with an ICMP Time Exceeded Message (TEM) that indicates that the datagram has expired.
- Note: "Normally" is right: Microsoft says some routers do not send the message and show as a row of asterisks. The statement's "probes" covers both the UDP datagrams of classic traceroute (RFC 2151, Cisco) and the echo requests of Windows tracert (Microsoft). The Cisco text restates RFC 2151 closely; it is a vendor page restating an RFC, so it counts, and Microsoft and RFC 1812 confirm independently in any case.

### entry "traceroute": lessons — ✅

- Note: `what-is-icmp` `term-traceroute` ("Traceroute", idea "Listing every router on the way") names the same tool. A router that does not answer still gets its row (shown as asterisks, per Microsoft), so the plainer idea does not contradict the definition.

## TTL

### entry "ttl": names — ✅

- Note: Names shown: "TTL" and "Time to Live". Both are given as names of this thing by the entry's statements ttl-ip-1 and ttl-dns-1 ("The TTL (Time to Live)"), and by RFC 791 §3.1 and RFC 1034 §3.6.

### entry "ttl", sense "ip": label — ✅

- Note: The label "In IP packets" names where the sense applies, and its three statements are about the IPv4 header field and its IPv6 counterpart.

### entry "ttl", sense "ip": statement "ttl-ip-1" — ✅

Claim: The TTL (Time to Live) is a number in every IPv4 packet's header, set by the sender.

- `rfc-791` §3.1
  > Time to Live:  8 bits
  >
  > This field indicates the maximum time the datagram is allowed to
  > remain in the internet system.
- `rfc-791` §1.4
  > The Time to Live is an indication of an upper bound on the lifetime of
  > an internet datagram.  It is set by the sender of the datagram and
  > reduced at the points along the route where it is processed.
- Note: RFC 791 defines the IPv4 header, in which the Time to Live field is a fixed part of every header (§3.1). The marker is correct.
- Note: Currency. RFC 791 is not obsoleted; none of its updates changes this field.

### entry "ttl", sense "ip": statement "ttl-ip-2" — ✅

Claim: Each router that passes the packet on lowers it by at least one, and at zero the packet is thrown away, so it cannot circle the network forever.

- `rfc-1812` §5.3.1
  > When a router forwards a packet, it MUST reduce the TTL by at least
  > one.
- `rfc-1812` §5.3.1
  > If the TTL is reduced to zero (or less), the packet MUST be
  > discarded
- `rfc-1812` §5.3.1
  > Its hop count function is critical
  > to ensuring that routing problems can't melt down the network by
  > causing packets to loop infinitely in the network.
- Note: RFC 1812 defines the router's handling of the TTL. The marker is correct.
- `rfc-1122` §3.2.1.7
  > The TTL field has two functions: limit the lifetime of
  > TCP segments (see RFC-793 [TCP:1], p. 28), and
  > terminate Internet routing loops.
- `rfc-1122` §3.2.1.7
  > it also has some attributes of a hop-count, since each gateway is required to reduce the TTL
  > field by at least one.
- Note: Two independent RFCs agree. Currency: RFC 1812 and RFC 1122 are not obsoleted, and their updates do not change TTL handling.

### entry "ttl", sense "ip": statement "ttl-ip-3" — ✅

Claim: In IPv6, the field that does this job is called the Hop Limit.

- `rfc-8200` §3
  > Hop Limit           8-bit unsigned integer.  Decremented by 1 by
  > each node that forwards the packet.  When
  > forwarding, the packet is discarded if Hop
  > Limit was zero when received or is decremented
  > to zero.
- Note: RFC 8200 is the Internet Standard that defines the IPv6 header and its Hop Limit field. The marker is correct.

### entry "ttl", sense "ip": lessons — ✅

- Note: `what-is-icmp` `term-ttl` ("TTL", idea "The hop counter on every packet") and `what-is-ip` `term-ttl` ("TTL", idea "The hop counter that stops loops") name the IP sense of TTL. RFC 1812 calls the TTL effectively a hop count limit, and stopping loops is the second statement. Neither idea contradicts the definition.

### entry "ttl", sense "dns": label — ✅

- Note: The label "In DNS" names where this sense applies, and both its statements are about the TTL of DNS records.

### entry "ttl", sense "dns": statement "ttl-dns-1" — ✅

Claim: In DNS, the TTL (Time to Live) is the number of seconds a record may be kept in a cache before the source has to be asked again.

- `rfc-8767` §4
  > TTL  a 32-bit unsigned integer number of seconds that specifies the
  > duration that the resource record MAY be cached before the
  > source of the information MUST again be consulted.
- Note: RFC 8767 §4 is the amended, current definition of the DNS TTL (it updates RFC 1034, 1035 and 2181). The marker is correct.
- `rfc-1034` §3.6
  > TTL             which is the time to live of the RR.  This field is a 32
  > bit integer in units of seconds, an is primarily used by
  > resolvers when they cache RRs.  The TTL describes how
  > long a RR can be cached before it should be discarded.
- Note: RFC 1034 defines DNS resource records and their TTL. The marker is correct.
- Note: Currency. RFC 1034 is not obsoleted; I read its TTL-related updates, RFC 2181 §8 (the value's range, and that it is a maximum) and RFC 8767 §4, and the statement holds under both. RFC 8767 is not obsoleted. True for a beginner: it leaves out RFC 8767's serve-stale exception.

### entry "ttl", sense "dns": statement "ttl-dns-2" — ✅

Claim: The administrator of the domain's zone sets it.

- `rfc-1034` §3.6
  > The TTL is assigned by the administrator for the zone where the
  > data originates.
- Note: RFC 1034 is the defining DNS standard for resource records. The marker is correct; RFC 2181 and RFC 8767 do not change who assigns the TTL.
- Note: "The domain's zone" is an everyday way of saying the zone the record comes from.

### entry "ttl", sense "dns": lessons — ✅

- Note: `what-is-dns` `term-ttl` ("TTL", idea "How long an answer may be kept: its time to live") names the DNS sense, and the idea is a plainer form of the definition.
