### entry "client": names — ✅

### entry "client": statement "client-1" — ✅

A client is the side that asks: a program that requests a service from another, the server, and uses the answer.

- `rfc-4949` §4
  > A system entity that requests and uses a service provided by
  > another system entity, called a "server".
- `rfc-9110` §3.3
  > An HTTP "client" is a program that establishes a connection to a
  > server for the purpose of sending one or more HTTP requests.
- Note: RFC 9110 is the defining standard for HTTP's terms, client and server among them; RFC 4949 is a separate document giving the general definition. Two independent sources.
- Note: RFC 4949 speaks of a system entity rather than a program, and RFC 9110 defines the HTTP client in particular; the statement's plainer wording is true in the ordinary case.
- Note: Currency: RFC 9110 (Internet Standard) and RFC 4949 (Informational) are not obsoleted.

### entry "client": statement "client-2" — ✅

On the web, the most familiar client is a browser sending HTTP requests to web servers.

- `rfc-9110` §3.5
  > The term "user agent" refers to any of the various client programs
  > that initiate a request.
  > The most familiar form of user agent is the general-purpose Web
  > browser
- `rfc-4949` §4
  > Example: The Word Wide Web, in which component servers provide
  > information that is requested by component clients called
  > "browsers".
- Note: RFC 9110 defines HTTP's user agents (the clients that start requests) and names the browser as the most familiar one; RFC 4949 independently gives browsers as the Web's clients.
- Note: Currency: both RFCs are not obsoleted.

### entry "client": statement "client-3" — ✅

Client and server are roles: the same program can be a client on one connection and a server on another.

- `rfc-9110` §3.3
  > The terms client and server refer only to the roles that these
  > programs perform for a particular connection.  The same program might
  > act as a client on some connections and a server on others.
- `rfc-4949` §4
  > In some cases, the server may
  > itself be a client of some other server.
- Note: RFC 9110 defines the HTTP client and server roles; this is its own wording, near enough.
- Note: Currency: both RFCs are not obsoleted.

### entry "client": lessons — ✅

- Note: The what-is-http term Client names the same thing; its idea (the side that asks, your browser) is a plainer form of client-1 and client-2.

### entry "html": statement "html-1" — ⚠️

HTML, the Hypertext Markup Language, is the web's core markup language: the text that describes the structure of a web page.

- `whatwg-html` §1.3
  > HTML is the World Wide Web's core markup language.
- `rfc-4949` §4
  > $ Hypertext Markup Language (HTML)
  > (I) A platform-independent system of syntax and semantics (RFC
  > 1866) for adding characters to data files (particularly text
  > files) to represent the data's structure
- Note: The HTML Standard (WHATWG Living Standard) is the current defining standard for HTML, and it confirms that HTML is the web's core markup language; RFC 4949 independently confirms a markup that represents a document's structure.
- Note: The full name is given only by RFC 4949. The HTML Standard never expands the abbreviation (searched in the saved copy, in §1.3 and the whole document), so the expansion has one source, which is not a defining standard.
- Note: Currency: the HTML Standard is the Living Standard, last updated 14 November 2026; RFC 4949 is not obsoleted.
Not confirmed: the expansion "Hypertext Markup Language" rests on RFC 4949 alone, with no second independent source and no defining standard stating it; a second citation that gives the full name would close this.

A page is written as a tree of elements and text, each element marked by tags such as <body> and </body>.

- Note: The HTML Standard is the defining standard for HTML documents, their elements and their tags.
- Note: It leaves out that some start and end tags may be omitted and implied; true in the ordinary case.
- Note: Currency: Living Standard, current.

### entry "http": statement "http-1" — ✅

HTTP, the Hypertext Transfer Protocol, is the main protocol of the World Wide Web: the one a browser uses to talk to web servers.

- `rfc-9110` §Abstract
  > The Hypertext Transfer Protocol (HTTP) is a stateless
- `rfc-9110` §1.2
  > HTTP has been the primary information transfer protocol for the World
  > Wide Web since its introduction in 1990.
- `microsoft-edge-https-first` §What are HTTP and HTTPS?
  > When you visit a website, your browser uses a protocol called HTTP (Hypertext Transfer Protocol) to communicate with the site — like a common language between your browser and the server.
- Note: RFC 9110 is the defining standard for HTTP and gives its full name; the Microsoft page independently gives the name and the browser-to-server use.
- Note: Currency: RFC 9110 is not obsoleted; the Microsoft support page is live and describes the current Edge.

### entry "http": statement "http-2" — ✅

It works by request and response: a client sends a request, and the server answers with a response that carries a status code.

- `rfc-9110` §1.1
  > The Hypertext Transfer Protocol (HTTP) is a family of stateless,
  > application-level, request/response protocols
- `rfc-9110` §3.4
  > A server responds to a client's request by sending one or more
  > "response" messages, each including a status code (Section 15).
- Note: RFC 9110 defines HTTP's message exchange and the status code.
- Note: It leaves out interim (1xx) responses before the final one; true in the ordinary case.
- Note: Currency: not obsoleted.

### entry "http": statement "http-3" — ✅

It is stateless: each request can be understood on its own.

- `rfc-9110` §3.3
  > HTTP is defined as a stateless protocol, meaning that each request
  > message's semantics can be understood in isolation
- Note: RFC 9110 defines this property of HTTP; the statement is its own meaning in plain words.
- Note: Currency: not obsoleted.

### entry "https": statement "https-1" — ✅

HTTPS, the Hypertext Transfer Protocol Secure, is HTTP sent over a connection secured with TLS.

- `rfc-9110` §4.2
  > | https      | Hypertext Transfer Protocol Secure | 4.2.2   |
- `rfc-9110` §4.2.2
  > The "https" URI scheme is hereby defined for minting identifiers
  > within the hierarchical namespace governed by a potential origin
  > server listening for TCP connections on a given port and capable of
  > establishing a TLS ([TLS13]) connection that has been secured for
  > HTTP communication.
- `rfc-9112` §9.7
  > Conceptually, HTTP/TLS is simply sending HTTP messages over a
  > connection secured via TLS [TLS13].
- `microsoft-edge-https-first` §What are HTTP and HTTPS?
  > HTTPS (Hypertext Transfer Protocol Secure) encrypts that data, keeping your information private and secure.
- Note: RFC 9110 defines the https scheme and its full name; RFC 9112 defines how HTTP/1.1 runs over TLS.
- Note: Currency: RFC 9110 and RFC 9112 are not obsoleted. RFC 9112 is updated by RFC 9931, on optimistic protocol transitions, which does not touch §9.7. The statement names TLS, the current protocol, not SSL.

### entry "https": statement "https-2" — ✅

Secured means the server has proved it acts for the name in the address, and the messages are kept confidential and protected from changes on the way.

- `rfc-9110` §4.2.2
  > In this context, "secured" specifically means
  > that the server has been authenticated as acting on behalf of the
  > identified authority and all HTTP communication with that server has
  > confidentiality and integrity protection that is acceptable to both
  > client and server.
- Note: RFC 9110 defines what secured means for the https scheme; the statement is this definition in plain words (the identified authority being the name in the address).
- Note: Currency: not obsoleted.

### entry "https": statement "https-3" — ✅

An https URL uses port 443 unless it names another port.

- `rfc-9110` §4.2.2
  > If the port
  > subcomponent is empty or not given, TCP port 443 (the reserved port
  > for HTTP over TLS) is the default.
- Note: RFC 9110 defines the https scheme's default port.
- Note: Currency: not obsoleted.

### entry "method": statement "method-1" — ✅

A method, or request method, is the part of an HTTP request that says what the client wants done with the resource it names, such as GET to fetch a copy.

- `rfc-9110` §9.1
  > The request method token is the primary source of request semantics;
  > it indicates the purpose for which the client has made this request
  > and what is expected by the client as a successful result.
- `rfc-9110` §9.3.1
  > The GET method requests transfer of a current selected representation
  > for the target resource.
- Note: RFC 9110 defines HTTP's request methods and GET; a copy of the resource is the statement's plain word for a representation.
- Note: Currency: not obsoleted.

### entry "method": statement "method-2" — ✅

Other standard methods include HEAD, POST, PUT and DELETE; POST sends data for the server to process.

- `rfc-9110` §9.1
  > This specification defines a number of standardized methods that are
  > commonly used in HTTP, as outlined by the following table.
- `rfc-9110` §9.3.3
  > The POST method requests that the target resource process the
  > representation enclosed in the request according to the resource's
  > own specific semantics.
- Note: RFC 9110 defines the standardized methods; its table lists GET, HEAD, POST, PUT, DELETE, CONNECT, OPTIONS and TRACE, and the statement says "include".
- Note: Currency: not obsoleted.

### entry "method": statement "method-3" — ✅

Method names are case-sensitive and by convention written in capitals.

- `rfc-9110` §9.1
  > The method token is case-sensitive because it might be used as a
  > gateway to object-based systems with case-sensitive method names.  By
  > convention, standardized methods are defined in all-uppercase
- Note: RFC 9110 defines the method token; the convention it states is for standardized methods, which the statement says more generally.
- Note: Currency: not obsoleted.

  > Normally, if your website loads all resources securely over HTTPS, visitors observe a lock icon in the address bar of their browser.
- Note: Two independent vendors' pages (Microsoft and Cloudflare).
- Note: The statement says "browsers such as Microsoft Edge", not every browser; some browsers show a different symbol for a secure connection (Chrome's help page names its secure symbol "Default (Secure)"), which the statement does not deny. Cloudflare adds that the lock also needs every resource on the page to load over HTTPS, a condition the statement leaves out.
- Note: Currency: both pages are live; Cloudflare's was last updated 21 October 2026.

### entry "padlock": statement "padlock-2" — ✅

It means the connection uses HTTPS and the site's certificate is valid, so what is sent can't be intercepted.

- `microsoft-edge-secure` §Verify the connection icon in the address bar
  > The website you’re visiting has a valid certificate issued by a trusted authority. The information sent to and from the site is secure and can't be intercepted by an attacker.
- `cloudflare-mixed-content` §Mixed content errors
  > This indicates your site has a working SSL certificate and all resources loaded by the site are loaded over HTTPS.
- `microsoft-edge-https-first` §What are HTTP and HTTPS?
  > If the site is secure (HTTPS), you’ll see a padlock icon before the URL.
- Note: Microsoft and Cloudflare are independent publishers; each states that the lock means HTTPS with a valid certificate.
- Note: "Can't be intercepted" is Microsoft's own wording for protection from eavesdropping; true in the ordinary case.
- Note: Currency: all three pages are live and describe current browsers.

### entry "padlock": statement "padlock-3" — ✅

It does not prove a site is trustworthy: sites with valid certificates can have a poor reputation.

- `microsoft-edge-secure` §Verify the connection icon in the address bar
  > However, even websites with valid certificates may have a poor reputation, so always check the URL in the address bar to be sure you’re on the intended site before you enter any information.
- `google-chrome-secure` §What each security symbol means
  > Even when connected to a site securely, always be careful when you share sensitive or personal information.
- `rfc-8555` §1
  > The CA is not required to attempt to verify the
  > requester's real-world identity.
- Note: Microsoft and Google are independent publishers; RFC 8555 adds why: the most common certificates check only control of the domain.
- Note: Currency: both help pages are live; RFC 8555 (Proposed Standard) is not obsoleted or updated.

### entry "path": statement "path-1" — ✅

In a URL, the path is the part after the host, such as /docs/page.html, that says which resource on that server is meant.

- `rfc-3986` §3.3
  > The path component contains data, usually organized in hierarchical
  > form, that, along with data in the non-hierarchical query component
  > (Section 3.4), serves to identify a resource within the scope of the
  > URI's scheme and naming authority (if any).
- `rfc-3986` §3
  > When authority is present, the path must
  > either be empty or begin with a slash ("/") character.
- `whatwg-url` §4.1
  > A URL path segment is an ASCII string. It commonly refers to a
  > directory or a file, but has no predefined meaning.
- Note: RFC 3986 defines the URI path component.
- Note: Strictly the path follows the authority (host and any port), and it identifies the resource together with any query; the statement says this more loosely, true in the ordinary case.
- Note: Currency: RFC 3986 (Internet Standard) is not obsoleted; its updates, RFC 7320 and RFC 8820 on URI design and ownership, do not change the path's syntax. The URL Standard is the Living Standard, last updated 14 November 2026.

### entry "path": statement "path-2" — ✅

It is usually names separated by slashes, and it ends at the first ? or #.

- `rfc-3986` §3.3
  > The path is terminated
  > by the first question mark ("?") or number sign ("#") character, or
  > by the end of the URI.
- `rfc-3986` §3.3
  > A path consists of a sequence of path segments separated by a slash
  > ("/") character.
- Note: RFC 3986 defines the path's syntax. The statement leaves out that a path also ends at the end of the URL; its "usually" covers paths without slashes.
- Note: Currency: not obsoleted.

### entry "path": statement "path-3" — ✅

In an HTTP request, the client sends the path, with any query, to the server.

- `rfc-9112` §3.2.1
  > When making a request directly to an origin server, other than a
  > CONNECT or server-wide OPTIONS request (as detailed below), a client
  > MUST send only the absolute path and query components of the target
  > URI as the request-target.
- `rfc-9110` §4.2.1
  > The hierarchical path component and optional query component identify
  > the target resource within that origin server's namespace.
- Note: RFC 9112 defines the HTTP/1.1 request-target; the origin form it describes is the most common one. Requests through a proxy, CONNECT and server-wide OPTIONS use other forms, which the statement leaves out.
- Note: Currency: RFC 9110 and RFC 9112 are not obsoleted; RFC 9931's update to RFC 9112 does not touch §3.2.1.

### entry "path": lessons — ✅

- Note: The what-is-http term Path names the same thing; its idea (which page or file on the site) agrees with path-1.

### entry "rendering": statement "rendering-1" — ✅

Rendering is how a browser presents a web page: it draws each element of the page's HTML so that it shows the reader what that element means.

- `whatwg-html` §15
  > this
  > section provides a set of suggestions for rendering HTML documents
- `whatwg-html` §15.1
  > In the absence of style-layer rules to the contrary (e.g. author style sheets), user agents are
  > expected to render an element so that it conveys to the user the meaning that the
  > element represents, as described by this specification.
- `whatwg-html` §1.10
  > HTML documents
  > might be rendered to a screen, or through a speech synthesizer, or on a braille display.
- Note: The HTML Standard defines the expected rendering of HTML documents.
- Note: "Draws" is the screen case; a page may also be rendered as speech or braille, and author style sheets can override the default presentation (rendering-2 covers styles). True in the ordinary case.
- Note: Currency: Living Standard, current.

### entry "rendering": statement "rendering-2" — ✅

How the page looks comes from its CSS style sheets, which describe how to present it.

- `whatwg-html` §4.6.8.23
  > The specified resource is a CSS style sheet that describes how to present the
  > document.
- `whatwg-html` §15.1
  > The suggestions in this section are generally expressed in CSS terms.
- Note: The HTML Standard defines the stylesheet link type and the default rendering of HTML.
- Note: A page with no style sheet of its own still has a look, from the browser's default rules (also written in CSS terms); the statement speaks of the ordinary page.
- Note: Currency: Living Standard, current.

### entry "rendering": lessons — ✅

- Note: The what-is-http term Rendering names the same thing; its idea (drawing the page from its HTML and styles) agrees with rendering-1 and rendering-2.

### entry "status-code": statement "status-code-1" — ✅

A status code is the three-digit number in an HTTP response that says how the request went, such as 200 (OK) or 404 (Not Found).

- `rfc-9110` §15
  > The status code of a response is a three-digit integer code that
  > describes the result of the request and the semantics of the
  > response
- `rfc-9110` §15.3.1
  > The 200 (OK) status code indicates that the request has succeeded.
- `rfc-9110` §15.5.5
  > The 404 (Not Found) status code indicates that the origin server did
  > not find a current representation for the target resource
- Note: RFC 9110 defines HTTP status codes, 200 and 404 among them.
- Note: Currency: not obsoleted.

### entry "status-code": statement "status-code-2" — ✅

Its first digit gives the class: 1xx informational, 2xx successful, 3xx redirection, 4xx a client error, 5xx a server error.

- `rfc-9110` §15
  > The first digit of the status code defines the class of response.
- `rfc-9110` §15
  > 1xx (Informational): The request was received, continuing process
- `rfc-9110` §15
  > 5xx (Server Error): The server failed to fulfill an apparently
  > valid request
- Note: RFC 9110 defines the five classes; the statement lists all five with RFC 9110's names (2xx Successful, 3xx Redirection, 4xx Client Error in the same list).
- Note: Currency: not obsoleted.

### entry "status-code": lessons — ✅

- Note: The what-is-http term Status code names the same thing; its idea (the number that says how it went) agrees with status-code-1.

- Note: URL and Uniform Resource Locator are given by url-1, which also calls a URL a web address; so all three names are given by this entry's own statements.

### entry "url": statement "url-1" — ✅

A URL, or Uniform Resource Locator, is a web address: it identifies a resource, such as a page or file, and says how to reach it.

- `rfc-3986` §1.1.3
  > The term "Uniform Resource Locator" (URL) refers to the subset of URIs
  > that, in addition to identifying a resource, provide a means of
  > locating the resource by describing its primary access mechanism
  > (e.g., its network "location").
- `microsoft-edge-https-first` §What are HTTP and HTTPS?
  > Web addresses (URLs) can begin with either HTTP or HTTPS.
- `rfc-4949` §4
  > In an FTP or
  > HTTP URL, the host name is followed by the path name of a file on
  > the server.
- Note: RFC 3986 defines the term URL and its full name; Microsoft independently calls URLs web addresses; RFC 4949 gives a file as the example resource.
- Note: RFC 3986 recommends the general term URI in new specifications, but URL remains the current everyday term (the WHATWG URL Standard uses it).
- Note: Currency: RFC 3986, RFC 4949 and the Microsoft page are current.

### entry "url": statement "url-2" — ✅

It has parts: a scheme such as https, a host with an optional port, a path, and sometimes a query and a fragment.

- `rfc-3986` §3
  > The generic URI syntax consists of a hierarchical sequence of
  > components referred to as the scheme, authority, path, query, and
  > fragment.
- `rfc-3986` §3.2
  > The generic syntax provides a common
  > means for distinguishing an authority based on a registered name or
  > server address, along with optional port and user information.
- `whatwg-url` §4.1
  > A URL’s port is either null or a
  > 16-bit unsigned integer that identifies a networking port.
- `rfc-9110` §4.2
  > | https      | Hypertext Transfer Protocol Secure | 4.2.2   |
- Note: RFC 3986 and the URL Standard each define a URL's components; RFC 9110 registers https as a scheme.
- Note: The statement leaves out the optional user information in the authority, and that some URLs (such as mailto) have no host; true for web addresses, the ordinary case.
- Note: Currency: all current.

### entry "url": lessons — ✅

- Note: The what-is-http term URL names the same thing; its idea (the web address of a page or file) agrees with url-1.
